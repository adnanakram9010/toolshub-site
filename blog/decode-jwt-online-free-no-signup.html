How to Decode a JWT Online

See exactly who a token is for, what it allows, and when it expires — in seconds, free, with no signup.

It is free, needs no signup, and the token never leaves your browser.

JSON Web Tokens show up everywhere: login sessions, APIs, single sign-on. They look like one long meaningless string, but they are structured — three parts joined by dots, each holding plain information once decoded. This guide shows you how to read one — and the mistake that catches almost everyone: thinking "decoded" means "verified".

What a JWT actually is

A JWT has exactly three parts, separated by two dots: header.payload.signature. Each part is base64url-encoded: a URL-safe base64 using - and _ instead of + and /, with no = padding. Decoding only reverses that encoding: a JWT is encoded, not encrypted, so anyone holding the token can read its payload.

  • Header — two fields: alg, the signing algorithm (for example HS256), and typ, "JWT".
  • Payload — the claims: who it is for (sub), what they may do (admin, role), when issued (iat), when it expires (exp). This is the part you need to read.
  • Signature — the proof of who issued the token. Only the secret key can check it, so a decoder without the key can show it but not verify it.

The tool warns: "The signature is not verified. This tool only decodes the token — it does not check who signed it." A decoded payload is a claim, not proof: anyone can write a token saying "admin": true; only a verified signature makes it trustworthy.

Decode a JWT in 5 steps

  1. Open the JWT Decoder — it runs entirely in your browser, so your token is never uploaded.
  2. Paste the whole token into the "JWT token" box — three parts separated by dots. Or click Use sample token.
  3. Click Decode. The tool splits the token on the dots and decodes the first two parts into JSON.
  4. Read the three boxes: Header and Payload as pretty-printed JSON, Signature as the raw third part — or "(empty)" if missing.

A worked example: decoding the sample token

Click Use sample token and the tool fills in this 195-character token:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImlhdCI6MTUxNjIzOTAyMiwiZXhwIjoxODkzNDU2MDAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

The header:

{ "alg": "HS256", "typ": "JWT" }

The header JSON is 27 characters, and 27 bytes encode to exactly 36 base64url characters (27 ÷ 3 × 4 = 36). HS256 means HMAC with SHA-256.

The payload:

{ "sub": "1234567890", "name": "John Doe", "admin": true, "iat": 1516239022, "exp": 1893456000 }

Claim by claim: the subject (sub) is user "1234567890", the name is John Doe, admin is true. The two numbers are Unix timestamps in seconds: iat 1516239022 is 18 January 2018, 01:30:22 UTC (issued), and exp 1893456000 is 1 January 2030, 00:00:00 UTC (expires). The payload JSON is 85 characters, encoding to 114 base64url characters. From 13 November 2026 that expiry is 1,144 days away — the tool reports the token as still valid. The 43-character signature is exactly what 32 bytes encode to — 256 bits, matching HS256.

A second example: an expired token

Take a token with this payload: {"sub": "demo-user", "role": "editor", "exp": 1700000000}. Its exp, 1700000000, is 14 November 2023, 22:13:20 UTC — already past. Paste it and click Decode: the header and payload decode normally, but the note reads that the token is EXPIRED, with the expiry date shown. The token is 151 characters (segments of 36, 70 and 43) and its signature is a placeholder, since the tool never verifies signatures. That is how you catch a stale session token.

5 mistakes that make JWT decoding go wrong

  • Treating "decoded" as "verified". Decoding reads the token; verification proves who signed it. A payload saying "admin": true means nothing until the signature is checked — never grant access on a decoded payload alone.
  • Putting secrets in the payload. Base64url is reversible by anyone holding the token — encoding, not encryption. Passwords, API keys and personal data do not belong in a payload; if it must stay secret, keep it out of the token.
  • Ignoring the expiry claim — or trusting a token without one. A token with no exp never expires, so a leaked one works forever. Always check the expiry note; a missing exp is a problem, not a convenience.
  • Pasting production tokens into random decoders. Many decoders send your token to a server. Ours runs entirely in your browser, but the safe habit is the same: use test tokens, or the built-in sample token. Never paste a live token with real user data into an unchecked site.
  • Copying only part of the token. A JWT needs all three parts: copying just the middle segment, or dropping the signature, gives the "exactly 3 parts" error. Copy from the first character to the last, with no spaces or line breaks, and check both dots are present.

Frequently asked questions

Is it free to decode a JWT online?
Yes. ToolsHub's JWT Decoder is free with no signup — paste a token and read its header, payload and expiry in seconds.

Does decoding a JWT verify its signature?
No. Decoding only reads the token; the signature is shown as it stands, unverified, so a decoded payload is not proof the token is genuine. Verification needs the secret key, on your own server.

What does the exp claim in a JWT mean?
The exp claim is the expiry time as a Unix timestamp in seconds. The decoder converts it to a date and says if the token is still valid or expired — the sample token expires on 1 January 2030.

Is it safe to paste a JWT into an online decoder?
With ToolsHub's decoder, yes for test tokens — everything runs in your browser and the token is never uploaded. Still, never paste a production token with real secrets into any website; use a test token or the sample.
